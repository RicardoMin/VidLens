# 问题驱动选图与图文讲解验证

本轮保留 **0.1.0**。新增问题选图、候选预览和精确取帧，让 AI 能检查一个过程的前态、中间变化和结果。自动词语匹配用于找候选，复杂图解的取舍交给实际看图的 AI。

## 为什么增加一次视觉复核

开发题使用中文 B 树插入演示。自动选图读过 88 个候选，必要的叶节点溢出、旧根溢出和新根状态都在候选池中，却最终选中了两组相近画面：输入清单反复包含题目里的数字，滚动页面又制造了新的词语和像素变化。它们挤掉了真正的中间步骤。

增加语音邻域惩罚、压低数字清单权重的离线尝试没有稳定解决问题，还可能误伤矩阵和数组课程。因此没有上线针对这道题的权重调整。原始不利选图、完整探针和分析均保留在私有实验目录。

最终实现分两层：

1. `read_frames(question=..., visual_queries=...)` 结合问题、附近原文和屏幕 OCR，探查原始变化序列及其前后状态。首轮最多 48 个候选，补查最多 48 个；只交付选中的原图。
2. 手写公式、树图和连线关系使用 `preview=True`。预览混合问题相关状态与时间覆盖，最多 24 格、每页 6 格。AI 实际看过后，按候选的 `read_timestamp` 取回关键原图；缺少转折时缩小范围再预览。

没有新增托管模型调用或运行依赖。首批全片阅读仍保持时间覆盖；问题选图和预览都是明确请求的路径。`visual_queries` 最多六项，由用户问题拆解成取证目标，不填入隐藏答案。

```text
问题与原文 → 局部变化候选 → 屏幕文字与邻近状态
                                      ↓
                       自动原图 / 带编号预览
                                      ↓
                       AI 看关系、选步骤、取原图
                                      ↓
                       带来源的讲解 → 独立复算
```

相关实现：[候选匹配](../../src/vidlens/visual_relevance.py)、[读取编排](../../src/vidlens/visual_query.py)、[预览分页](../../src/vidlens/visual_preview.py)。参考了 [LongVideoAgent](https://github.com/longvideoagent/LongVideoAgent) 的语音定位与视觉查询分工，以及 [VideoRAG](https://arxiv.org/html/2501.05874v3#S2.SS3) 面向问题与最终回答选择材料的方向；本轮效果由下述实际实验检验。

## 验证设置

| 案例 | 范围 | 必须追踪的内容 |
|---|---|---|
| [B 树插入](https://www.bilibili.com/video/BV1sj411b7XC/?p=1) | 0–270 秒，开发题 | 插入 26 引起叶节点与根的两级分裂 |
| [B 树删除](https://www.bilibili.com/video/BV1sj411b7XC/?p=1) | 170–439 秒，留出问题 | 两个独立例子的连续借位、根替换及最终树 |
| [Online softmax](https://www.bilibili.com/video/BV1FM9XYoEQ5/?p=6) | 220–720 秒，留出问题 | 手写 d0→d1→d2 的缩放与提取过程 |
| [CUDA／NCU GEMM](https://www.bilibili.com/video/BV1nkgN6LE7h/?p=1) | 365–845 秒，补充问题 | 实际命令、测量值、管线、缓存和 L2 警告 |

B 树开发题与删除题来自同一视频，并共享部分初始状态，不能视为完全独立的视频泛化测试。CUDA 案例在前两题出现评分上限后加入；它的题目、参考和复算题也在选图前独立冻结，算法没有据其结果调参。另查看过 PyTorch 张量操作视频，因内容仍较容易由通用规则复算，未纳入最终对照。

每对作者使用**相同 MLX large-v3-turbo 转写、相同问题、相同写作指南、各四张原图**，分别独立写作。基线图片按当前产品的时间覆盖方式选取；新流程先看预览，再选择原图。作者可以在正文中使用其中两至四图，也可用明确的推导和示意连接步骤。

独立评阅者不知道条件映射，实际打开作者收到的图片，按冻结量表评估事实 20 分、讲解 8 分、图文支撑 8 分。另两位独立读者分别只看对应讲解，做两道复算题，共 8 分。正确推导不会因缺少某张截图而自动扣分；图片事件覆盖另记，不混成答案质量分数。这是 AI 作者、AI 评阅与 AI 读者的单次对照，不是人类用户研究。

## 最终结果

| 案例 | 固定量表：旧 → 新 | 独立读者复算：旧 → 新 |
|---|---:|---:|
| B 树删除 | 44/44 → 44/44 | 8/8 → 8/8 |
| Online softmax | 44/44 → 44/44 | 8/8 → 8/8 |
| CUDA／NCU | 41/44 → 44/44 | 8/8 → 8/8 |

CUDA 的分差来自实际程序路径缺项、DRAM 数值误读和命令原图缺失，各一分；新流程补齐了这些信息。其事实子项从 18/20 到 20/20，图文支撑从 7/8 到 8/8，讲解清晰度保持 8/8。三组独立读者的复算均没有分差。

复核也发现新 CUDA 原稿把 L1/TEX 吞吐率 96.11% 写成约 93%。这项额外数值没有单列在冻结事实子项中，因而单独记录为非计分错误，没有事后改量表。**44/44 表示通过这些固定检查项，不能当作全文完全正确。** 交付样例另存一份，已纠正该值，并撤下无法可靠核对的 Store 精确末位；评分与哈希继续对应原稿。写作指南补充了按字段名、数值、单位和统计口径共同核对的流程，这条后续提醒没有被计成已验证的评分收益。

这轮确认了部分实测信息和原图过程更完整，也暴露了看过正确画面后仍会误读相邻指标的问题。尚未测出讲解清晰度或独立读者理解成绩的提升。

前两题的原始评阅在迁移题评分前已保存；后续复核没有改变其分数。B 树旧讲解用两张原图和正确的文字树图补出了过程，因此符合冻结标准，不能为了显示新方法更好而额外扣分。新讲解实际配图覆盖从三项完整事件，增加到四项完整、一项部分可见；softmax 两侧均覆盖四项事件。

CUDA 参考另经过原图与 NVIDIA 官方定义核对。L2 警告的 sector 数、32 B 的 sector 尺寸、128 B 的 cache line 不能混成“应用真正用了多少字节”；模糊的 Store 小数末位移出了硬评分。Compute／Memory 总览也是子指标聚合，不能据此把浮点管线或 DRAM 当作同样饱和。参见 [Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html) 与 [Compute Triage](https://docs.nvidia.com/nsight-compute/ComputeTriage/index.html)。

公开数据：[问题与条件](../../benchmarks/question-cases.json)、[评分与选图成本](../../benchmarks/results/question-visual.json)。原始转写、图片、匿名包、初评、复核与文件哈希保留在 `.vidlens`，不进入发行包。

## 额外成本与实际边界

新流程最后交给作者的原图数量仍为四张，但选图阶段多看了预览，**这不是同 token 预算的比较**。

| 案例 | 预览拼图 | 候选格数 | 局部补预览 | 原图复核 |
|---|---:|---:|---:|---:|
| B 树删除 | 8 | 45 | 1 次 | 4 张 |
| Online softmax | 4 | 23 | 0 次 | 4 张 |
| CUDA／NCU | 4 | 24 | 0 次 | 4 张，另裁 1 图 |

这些是实际读取量，不是模型账单。首次下载、ASR、区间扫描、OCR 与看图分别记录；候选文件已缓存后的重复读取不能当作首次速度。B 树局部补预览遇到 OCR 沙箱警告，图片仍可用，选图者依据实际图片完成判断；CUDA 的小字仍受原始 480p 流限制，裁剪不能恢复不存在的细节。

## 修复与交付验证

| 问题 | 修复后的行为 |
|---|---|
| 平台时长取整，概览把末帧推进到真实视频之后 | 对扫描器的末帧保留实际 PTS；真实 B 树 438.3 秒末帧可正常读取 |
| 长时间停留画面的源 PTS 早于请求区间 | 按请求时间匹配语音和区间，保留源 PTS 引用，预览提供 `read_timestamp` 回取 |
| 请求区间内没有新的画面变化，预览为空 | 采样区间内实际正在显示的画面 |
| 探针在版本校验前写入证据数据库 | 媒体与语音版本校验后统一保存，失效读取不写入主证据表 |
| 局部扫描游标与整片游标混淆、后页失败被隐藏 | 返回扫描 ID、范围、作用域，传播部分失败状态 |
| 重复图片去重抹掉恢复原状的步骤 | 只合并相邻相同图片，保留 A→B→A 的返回状态 |
| 预览误记作原图交付、图片计数遗漏 | 预览单独计数，仅成功发送的原图登记原图交付 |
| OCR 无文字或没有问题词，仍像是成功理解画面 | 明确时间覆盖回退和无匹配状态；语音命中与屏幕命中分别记录 |

完整离线回归 **395 项通过**，Ruff 与 skill 校验通过。全新临时环境安装 wheel，在项目外启动实际 stdio MCP，验证了 13 个工具、4 张预览、23 个候选、精确取回 4 张原图与时间映射；预览没有产生原图交付记录。安装后的 25 个源码模块与工作区一致，发行包未包含模型、视频或私有缓存。

```sh
# 问题预览：查看返回的图片，再从元数据选 read_timestamp
.venv/bin/python -m vidlens --home .vidlens frames VIDEO_ID 365 845 \
  --question '结合报告的实际指标解释这次 GEMM 的瓶颈' --preview

# 精确取回选中的原图；时间来自本次预览，不照抄示例
.venv/bin/python -m vidlens --home .vidlens frames VIDEO_ID START END \
  --timestamps TIME_1 TIME_2 TIME_3 TIME_4

# 已获取原视频和转写后，生成私有对照材料
.venv/bin/python benchmarks/evaluate_question_frames.py \
  --home .vidlens --questions benchmarks/question-cases.json \
  --case cuda-ncu-gemm-screen-2026-11-06 --split heldout --preview \
  --packets .vidlens/question-review --output .vidlens/question-selection.json
```

脚本只生成原文和图片条件，不把候选数或词语命中转成讲解质量分。运行真实对照还需要独立作者、冻结参考和读者复算。下一步应扩大视频特有状态与实测数值的题集，并检验局部预览是否能减少每次为缺失步骤重新寻找画面的成本。
