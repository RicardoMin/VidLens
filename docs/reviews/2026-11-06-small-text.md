# 低清图表与小字：取证、读数和复现分开验证

这轮增加了原尺寸局部阅读，并用 **MySQL、Wireshark、分类模型评估三条中文视频**做对照。结果没有支持“图片处理升级后，最终讲解自然更准”：两类案例持平，新流程的网络讲解出现两处十倍误读。独立复核找出了错误，后续核对流程与交付稿据此修正，原始成绩完整保留。

## 产品改动

`read_detail` 将同一时刻的上下文和源像素 PNG 局部块一起返回。AI 可以看清表头、坐标轴和实验归属，再检查小字；六个区域内最多十二块，每块最多 1920×1080，相邻块至少重叠 64 像素。超过预算会要求缩小区域，不悄悄丢掉右侧或底部内容。

```python
read_detail(video_id, timestamp,
            boxes=[[0.0, 0.55, 1.0, 0.23]],
            upgrade_source=True)
```

这里的区域只是调用示例，实际需要按图选择。`timestamp` 使用已读取帧的真实时间。

- **更少的二次损失。** 独立 PNG 解码路径保留源图，局部不插值放大；OCR 优先读取保留源图而非显示缩略图。源像素缓存上限为 3840×2160。
- **清楚区分三种尺寸。** `decoded_source_size` 是解码源尺寸，`source_size` 是保留源尺寸，MCP 的 `transmitted_size` 是实际交付图片尺寸。请求档位与获取状态另行记录。
- **升级不损坏裁剪坐标。** 同时检查宽高比和两个方向的像素数，不能只按总面积选源。普通取帧保留同来源的高质量缓存；来源变化使旧证据失效，旧源损坏时可用成功的新解码恢复。
- **交付状态准确。** 原图、局部块和 OCR 分开记录；成功交付上下文才登记完整帧，多个裁块不虚增已读画面。

CLI 对应 `detail VIDEO_ID TIMESTAMP --box X Y W H --upgrade-source`。MCP 默认提供 15 个工具，高级模式 20 个；更新后需重连 MCP。

## 为什么采用局部读取

先在开发夹具上比较了源尺寸、分块尺寸、显示放大和 OCR 参数。一个 3840×2160、24 像素字号的中英技术表，在整图与 1920×1080 显示图中没有识别出文本；取 1020×390 原尺寸区域后，七行数字与单位都正确，包含 `ms`、`MB/s`、`GiB/s`、百分数和 warp。三种块尺寸都识别出同样七行，因此保留较大的块以减少图片数量。

降低 Vision 的最小文字高度阈值没有改善这些整图。英文优先损害了中文，三倍放大也曾引入新的汉字错误，所以没有把这些处理设为默认。[Apple 文字高度说明](https://developer.apple.com/documentation/vision/vnrecognizetextrequest/minimumtextheight)及[识别指南](https://developer.apple.com/documentation/vision/recognizing-text-in-images)提供了参数依据；实际取舍依据本地实验。

这些是开发夹具结果，不能代替真实视频讲解评测。

## 三条新视频

| 类型与证据 | 检查片段 | 实际源尺寸 | 主要陷阱 |
|---|---:|---:|---|
| [MySQL EXPLAIN](https://www.bilibili.com/video/BV11V4y1R73P/?p=8) | 00:00–02:18，4 帧 | 808×480 | `>=` 与 `>`、额外价格谓词、估计行数、filtered |
| [Wireshark I/O Graph](https://www.bilibili.com/video/BV1wx1kBvEjq/?p=1) | 01:08–05:01，4 帧 | 852×480 | 秒与毫秒、字节与速率、曲线倍率、在途量与窗口 |
| [分类指标与混淆矩阵](https://www.bilibili.com/video/BV1Sq4y1L7B2/?p=1) | 09:36–14:36，6 帧 | 852×480 | 25 格计数、行列方向、micro 平均、不同运行的结果 |

本次实际能取得的公开视频轨道均为 480p。请求更高档位没有得到更多源像素，不能把 `2160` 的请求参数写成“取得 4K”。取证使用上述片段与固定时间点，没有声称完整观看三个视频。

问题、源图、原始转写、事实参考和复现输入先冻结，再独立生成两套讲解。基线采用已有事实核对流程、JPEG 和裁剪；新流程采用 PNG、`read_detail` 及同样的事实核对。双方都能做确定性显示放大，每个案例最多实际看图 18 次；问题、语音、时刻与文字长度约束相同。

两名独立读者各只看一套讲解及嵌入图片，另有只看题面的对照。裁判按 P/Q 盲化稿逐项审查，既审预设事实，也审正文、代码、图注中新增的数字。六篇共 **408 处数字**全部绑定到原文位置与证据判断。讲解、读者答案及程序先冻结，之后执行原定输入，不把失败反馈给读者补做。

## 原始结果

| 检查项目 | 原流程 | 原尺寸细读 | 结论 |
|---|---:|---:|---|
| MySQL 的两条谓词与主要 EXPLAIN 数字 | 正确 | 正确 | 未测出提升 |
| Wireshark 决定结论的源值误读 | 0 处 | 2 处 | 新稿退步，见下文 |
| 混淆矩阵 25 格、转置条件与 P/R | 正确 | 正确 | 未测出提升 |
| 三项程序复现 | 3/3 | 3/3 | 两侧各 12 个冻结输入全部通过 |
| 九道读者任务完整通过 | 8/9 | 7/9 | 其余为部分通过，不能被代码成绩掩盖 |
| 作者实际看图次数：SQL／网络／分类 | 10／11／16 | 9／11／12 | 不是模型账单或速度增益 |

新稿把 RTT 显示因子 `17000000` 抄成 `1700000`，又将发送平台约 `750000` 读成约 `75000`。后续运算虽然自洽，却把对应吞吐算成约 12 Mbit/s，正确数量级约为 120 Mbit/s。错误传播到多个句子、公式和代码位置；九条关键问题记录包含重复传播，不能说成九种独立数字错误。

这也解释了为什么代码仍然通过：网络复现程序从原始包字段按 50 ms 分桶，不使用显示倍率。程序通过证明了分桶、方向过滤和换算步骤，不能证明讲解抄对了图表源值。相应文字题保留了失败部分。

两套讲解也有共同缺项：没有充分区分 BIF 与发送端 cwnd，未明确 `key_len` 的字节单位，未讲训练表现与新测试集泛化的关系。31 条复合事实中，原流程为 27 正确、1 部分单位缺失、3 遗漏；新流程为 26 正确、1 数值错误、1 部分单位缺失、3 遗漏。`key_len=4` 的值本身正确，不能把少写单位描述成“单位写错”。金额币种在源视频未说明，未声明币种也没有被算成错误币种。

只看题面的对照无法恢复两条 SQL、网络参数和源视频矩阵，但能完成通用矩阵指标变体。读者还能凭已有知识补出讲解漏掉的泛化关系，所以这些正确回答不倒推为作者已讲清楚。这是 AI 读者代理实验，尚未开展真人学习测验。

## OCR 与最终核对

盲测作者调用 Vision 时遇到受限环境的 `-6662` 图像缓冲区错误，依靠实际图片继续工作；这与“OCR 正常运行但没认出字”不同。后来在主机权限下、独立缓存中运行相同生产 OCR：三条视频都返回了文字，但仍会将 SQL 的比较符读错、漏掉网络倍率，或把矩阵数字认错。该补充诊断未回填冻结作者输入，也未用于重算成绩。

据此，[事实核对流程](../../skills/read-video/references/fact-checking.md)增加了“只看源图的第二遍读数”：先记录原始字符串、单位、时间与区域，再与草稿比较；长数字同时按三位分组记录，曲线必须连同相邻刻度和整轴数量级读取。派生计算与全文图注随后按这个记录复查。独立读数与修改稿是后续纠错，不替换上表的原始对照结果。

额外读数也不是金标准。后续复读曾在看见草稿后改判零的数量，随后用另一名未看草稿的读者与源像素字符位置交叉检查：RTT 因子含六个零，邻近刻度 `750000` 含四个零，确认原稿确有十倍误读。控制台多位小数则出现过读法分歧，交付稿去掉了并非解释所必需的精确背景数值，保留预存图片与当前运行的来源区别。这个诊断消耗了额外看图次数，不能把它包装成原盲测预算内的改善。

## 可复现材料

- [结构化案例与参考事实](../../benchmarks/detail-cases.json)：源链接、时间点、事实条件和冻结输入，不包含原视频、转写或本机路径。
- [读者问题](../../benchmarks/detail-questions.json)：保留三个案例的原题。
- [读者执行器](../../benchmarks/evaluate_detail_reader.py)：真实运行提交的函数，检查源值重建与原有变体，记录输入、观察值及哈希。
- [分项结果](../../benchmarks/results/small-text.json)：保留各案例、条件、全文数字审核和复现成绩，不合成总分。

先检查读者提交的是本案例的有限计算，再运行：

```sh
.venv/bin/python benchmarks/evaluate_detail_reader.py \
  --case wireshark_io_graph_units \
  --reader /absolute/reader.md --code /absolute/reader.py \
  --output /absolute/execution.json
```

SQL 检查谓词与 NULL／边界条件；网络检查方向过滤、缺字段、十进制桶边界和速率单位；分类检查源矩阵重建、非对称矩阵和零分母。它们是明确输入上的教学复现，没有重跑原数据库、原始 pcap 或训练任务。事实真伪仍要对照实际图像审核，`evaluate_fact_review.py` 负责检查审核记录的完整性与归属。

评测中的媒体、转写、原稿、图片和完整逐断言记录保存在私有 `.vidlens/detail-reading-2026-11-06`；源文件与提交均有 SHA256。公开参考去除了私有路径，文件哈希因此不同；预期输入与答案逐项保持相同，原始实验日志继续绑定原冻结参考。

工程验证：483 项离线测试、Ruff、skill 校验通过。v0.1.0 在独立 site-packages 环境中通过真实 stdio MCP 验证：15／20 个工具、真实低清媒体的 PNG 解码、上下文 JPEG 与两块 PNG 的尺寸／索引／像素对应、仅成功上下文计入全帧交付，以及损坏上下文后的恢复。安装包源码与工作区逐字节比对；缓存、模型与本机配置没有进入包。
